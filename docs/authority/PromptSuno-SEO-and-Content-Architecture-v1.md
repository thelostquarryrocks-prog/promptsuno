# PromptSuno SEO and Content Architecture v1
Status: CURRENT / AUTHORITATIVE
Effective: 2026-09-27

## 1. Purpose

PromptSuno must be excellent at two things simultaneously:

1. A fast, crawlable, useful educational product that can earn organic search traffic.
2. A rich, app-like creative workspace with advanced interactive tools such as Sound Brain, Lyrics Studio, and Prompt Doctor.

Do not force one layer to compromise the other.

Preferred architecture:

LEARN / SEO layer
→ fast server-rendered or statically generated HTML where appropriate
→ minimal JavaScript
→ crawlable and useful without an account
→ answer-first, task-oriented content

BUILD / FIX product layer
→ richer React interaction
→ Three.js / WebGL where appropriate
→ stateful workflows
→ authenticated/premium capabilities where useful

Heavy interactive code should load only where it provides product value.

## 2. LEARN is the primary organic acquisition surface

LEARN should be the main search-driven educational layer.

A strong Learn page should:
- answer a real user question quickly
- remain useful without an account
- render meaningful crawlable HTML
- begin simple and progressively reveal advanced depth
- include original examples, screenshots, or interactive demonstrations where useful
- distinguish documented behavior from uncertain or experimental guidance
- connect naturally into BUILD or FIX
- remain fast on mobile
- avoid unnecessary client-side bundles

Do not make Sound Brain itself responsible for ranking for every Suno query.

Preferred acquisition loop:

Search intent
→ useful Learn page
→ explanation / example
→ contextual CTA into Sound Brain, Lyrics Studio, or Prompt Doctor
→ user enters the product with relevant context preserved where practical

## 3. Stable, version-resilient URLs

PromptSuno.com is version-agnostic.

Prefer stable canonical URLs built around user jobs and durable topics rather than embedding a current Suno model number into every path.

Illustrative examples:
- /learn/style-prompts
- /learn/song-structure
- /learn/vocals
- /learn/lyrics
- /learn/reference-audio
- /learn/editing
- /learn/variety
- /build/sound-brain
- /build/lyrics
- /fix/prompt-doctor

These are examples, not a frozen sitemap.

A page can clearly state its current model/version scope inside the content, for example:
"Current guidance for Suno V6 — reviewed September 2026."

When Suno changes, update or version the content without needlessly changing the canonical URL.

Do not automatically inherit old SunoV6.wiki route architecture.

## 4. Content architecture principles

Prefer fewer, stronger canonical pages.

Every indexable page should satisfy a distinct user intent and provide enough original value to justify its existence.

Avoid:
- one-keyword-one-page generation
- thin autogenerated pages
- duplicate or near-duplicate intent pages
- generic AI summaries
- keyword stuffing
- doorway pages
- pages created only because a keyword exists
- mass-generated "best prompt for X" pages without original value

PromptSuno's durable content moat should come from the combination of:
- official Suno documentation
- current community evidence
- audiovisual evidence
- PromptSuno research
- original experiments where actually performed
- Prompt Doctor failure patterns
- Sound Brain musical taxonomy and relationships
- concrete examples
- interactive demonstrations

Do not fabricate experiments or measured outcomes.

## 5. Beginner → advanced progression

LEARN content should generally begin with the simplest useful answer and progressively reveal complexity.

Useful structure:
1. Fast answer
2. Why it matters
3. Step-by-step workflow
4. Example
5. Common mistakes / failure cases
6. Advanced considerations
7. Optional Sources & testing notes
8. Next useful action in BUILD or FIX

"Beginner → Advanced → Pro" should usually be the shape of the content, not a mode selector users must understand before reading.

## 6. Research should improve content quietly

Research rigor is a product advantage, but public pages should not feel like academic reports.

Translate evidence naturally.

Examples:
- "Suno documents..."
- "Results vary..."
- "Worth experimenting with..."
- "Community reports are mixed..."
- "This is not a guaranteed control..."

Where helpful, include an optional "Sources & testing notes" disclosure.

Keep evidence class and confidence available internally even when public copy uses simpler language.

## 7. Cross-pillar internal linking

LEARN, BUILD, and FIX should reinforce one another.

Required product/content loop:
- LEARN → BUILD
- BUILD → LEARN
- BUILD → FIX
- FIX → LEARN
- FIX → BUILD
- LEARN → LEARN

The product should feel like one connected system rather than three silos.

## 8. Interactive components inside content

Interactive components may appear inside Learn pages where they materially improve understanding.

Examples:
- a tiny style-example explorer
- a before/after prompt comparison
- an interactive structure diagram
- a small Sound Brain concept preview
- a Prompt Doctor example

Do not load the complete production Sound Brain WebGL experience on ordinary Learn pages merely because it exists.

Prefer lightweight embedded interactions and hand off to the full tool when the user chooses to continue.

## 9. WebGL / Three.js boundary

Sound Brain can remain a sophisticated Three.js / WebGL application without harming the SEO strategy.

Keep WebGL scoped to routes and surfaces where spatial interaction earns its cost.

LEARN pages should not require WebGL to:
- render primary content
- expose headings and links
- answer the target query
- expose metadata
- provide usable navigation

Do not make primary educational information available only after client-side WebGL or JavaScript execution.

## 10. Technical SEO baseline

For production indexable pages:
- meaningful HTML should be available without waiting for heavy client interaction
- use descriptive page titles and metadata
- use one intentional canonical URL per page
- keep navigation links crawlable
- generate and maintain a sitemap
- use meaningful HTTP status codes
- maintain semantic heading structure
- keep content accessible to keyboard and screen-reader users
- keep public pages usable when optional interactive JavaScript fails
- preserve URL integrity
- avoid putting private prompts, lyrics, or user data into URLs
- keep staging and preview environments out of search indexes
- connect Search Console after production launch
- establish Core Web Vitals and performance monitoring

Structured data should only be added when it truthfully describes the page and is supported by current search-engine documentation. Do not treat structured data as a ranking guarantee.

## 11. Performance boundary

LEARN:
- minimize initial JavaScript
- optimize images and fonts
- use static/server rendering where appropriate
- lazy-load optional interactive components
- avoid loading Three.js unless required

BUILD / FIX:
- preserve interaction quality
- lazy-load expensive modules where appropriate
- optimize WebGL/mobile rendering
- keep route-level code splitting strong
- avoid sending research corpora or unnecessary internal data to the client

Performance budgets should eventually be defined for JavaScript, images, fonts, interaction latency, layout stability, WebGL startup, and mobile memory use.

## 12. Runtime research-data boundary

The internal research corpus is not the public runtime dataset.

Do not ship entire research-rich knowledge bases to the browser.

Prefer explicit, curated, deny-by-default projection from research sources into:
- public educational content
- bounded tool rules
- evidence snippets
- product-safe structured records

Raw research records, internal notes, private identifiers, large source payloads, and irrelevant provenance must remain server-side or offline unless explicitly projected.

## 13. Monkey Methods as contextual learning

Monkey Methods should operate as small contextual learning interactions distributed throughout the product.

STATIC
- tied to a specific UI concept
- one stable tip
- can remember that the user has opened it

ROTATING
- tied to a contextual tip bank
- avoid repeating already-seen tips until the available bank is exhausted
- then begin a new cycle
- the user should not be forced to consume tips

For anonymous users, local browser state is sufficient initially.

Account synchronization can be added later if it creates meaningful value.

Do not require a database round-trip for every tooltip interaction.

## 14. Seamless product continuity

Active creative work should feel continuous across BUILD and FIX.

A user should be able to move from:
Sound Brain
→ Lyrics Studio
→ Prompt Doctor

without copying/re-entering project context manually.

Active work can remain local/client-side while the user is editing.

Persistence should occur deliberately when saving, syncing, or using account features.

Long-term, structured Song Intent should be the shared state underneath this continuity rather than a chain of flattened text strings.

## 15. Premium and SEO

The free product must remain genuinely useful.

Do not damage organic growth by hiding the core Learn experience or basic usefulness behind authentication/paywalls.

Premium should appear at natural moments where additional value exists, for example:
- saving/syncing deeper project history
- advanced variants
- expanded Sound Brain library
- deeper relationships
- advanced Lyrics controls
- advanced Prompt Doctor features
- cross-tool project continuity beyond the free allowance

Avoid intrusive upgrade popups that interrupt ordinary learning and creation.

Do not promise unlimited use until API/model economics are known.

## 16. Vercel deployment / indexation rule

PromptSuno uses Vercel.

Production:
- main branch
- promptsuno.com
- indexable when launch-ready

Staging:
- staging branch
- staging.promptsuno.com
- not indexable

Feature / Codex branches:
- Vercel Preview Deployments
- not indexable

Search-engine discovery should only occur on intentionally published production content.

## 17. Historical source treatment

The pre-Three.js Gemini conversation "Building a Suno Web App" contributed several durable concepts adopted here:
- decouple crawlable guide content from heavier application logic
- mobile-first PWA/app-like experience
- seamless continuity between tools
- local-first active workspace state
- rotating/non-repeating tip behavior
- non-invasive premium philosophy
- Git/Vercel preview workflow
- SEO as a first-class requirement

The conversation is NOT itself a current authority.

Do not migrate its pre-research Suno behavior claims, diagnostic regex rules, exact database schema, or old frontend implementation assumptions as facts.

In particular, do not inherit unsupported deterministic rules about:
- prompt-length limits
- syllable thresholds
- bracket syntax
- punctuation/capitalization effects
- "ignored words"
- duet tags
- genre conflicts
- mandatory constraints
- other claimed hidden Suno behavior

Current PromptSuno research and current repository architecture supersede those assumptions.
